# MSP Phase 1 Design — Sync Controller

> Design document, approved 2026-09-01. Every decision here was settled in a
> grilling session with the repo owner; this file is the write-up, not a
> proposal. The implementation plan is a separate, later document.

**Goal:** Phase 1 delivers the Sync Controller of MSP-SPEC-001 §5: a Kubernetes
controller that takes a declared `ModelDeployment`, resolves and pins its image
digest, runs the Phase 0 conformance gate against that exact digest, copies the
verified image into the platform's internal registry, and reconciles a native
Deployment + Service + HPA from the model's own manifest — implementing the §5.3
state machine, the digest-identity rules of §5.4 (as far as Phase 1's
persistence allows), the GitOps tree shape of §9, and the §11 Phase 1
acceptance items. Vocabulary is `CONTEXT.md`'s: a *Version*'s true identity is
its *Digest*, *Conformance* is the only door into the platform, and several
pieces below are explicit *Stand-ins*.

**Spec:** `MSP-SPEC-001-model-serving-platform.md` §5, §9, §11 Phase 1, §12
(Q5). Glossary: `CONTEXT.md`. Layout authority: `docs/SCAFFOLDING.md` (which
this design changes — see [Layout](#layout)).

---

## 1. Scope and posture

**D1 — the dev environment is only the slice Phase 1 needs.** The
dev-environment ticket (#6) is built down to a `kind` cluster and two local
registries. Kafka, NATS JetStream and the LGTM stack are deferred to Phase 3/4
— the phases that first use them. Standing them up now would be scaffolding
for later; later can scaffold for itself.

**D2 — the contract freeze co-sign (#8, milestone S1 of the execution
plan) is treated as satisfied.** Phase 0
acceptance is the co-sign in practice: the envelope proto has not moved since.
Recorded here so nobody re-litigates it; if the proto ever moves, that is a
frozen-interface change with its own ticket regardless.

**D3 — the controller runs out-of-cluster (STAND-IN).** The Sync Controller
runs on the developer's host — controller-runtime's standard `make run`
posture — watching the kind cluster's API server. This is not laziness for its
own sake: it is what lets the controller import `msp/internal/conformance`
directly and drive the host's Docker daemon, so **not one line of conformance
code changes** for Phase 1. The production posture is in-cluster with a
dedicated conformance pool (spec §1.5); swapping postures is a later ticket,
and nothing in this design's interfaces depends on where the process runs.

**What Phase 1 delivers, exhaustively:** the §5 state machine, digest pinning,
conformance integration, internal-registry push, and reconciliation to native
Deployment + Service + HPA. Nothing else. In particular, spec §12 Q5's
companion requirements for the namespace split (green ResourceQuota, blue
PriorityClass) are outside it: they protect blue from green under contention,
and Phase 1 deploys into an empty local cluster with nothing to contend for.
Recorded in Stand-ins, to land with the first phase that runs blue and green
workloads together.

**Toolchain posture:** no kubebuilder CLI scaffolding and no ArgoCD. The
controller uses the controller-runtime *library* directly; the CRD YAML is
generated by `controller-gen` and committed. Locally, `kubectl apply` on the
GitOps tree stands in for ArgoCD sync — the controller watches the API server
either way, so the substitution is invisible to it.

## 2. State machine

Spec §5.3 defines the phases; this design adds the entry validation, the
failure edges, and the `Deployed ⇄ Deployable` edge (D4). `Declared` below is
spec §5.3's name for the state before the controller has touched the object —
it is not a value of `status.phase`, which is empty until the first successful
reconcile writes `Syncing`.

```
  kubectl apply
       │
       ▼
   Declared ──── cluster/namespace map checks out ────▶ Syncing
       │                                                  │ tag resolved at model-center
       │ map mismatch                                     │ registry; digest pinned into
       │                                                  │ spec + status; manifest
       │            CR model/version ≠ image manifest     │ extracted and cross-checked
       │          ┌───────────────────────────────────────┤
       ▼          ▼                                       ▼
     Rejected ◀───┬──────────────────────────── ConformanceRunning
    (terminal,    │  report has failing checks            │ report all-pass; image copied
     reason in    │  — or internal-registry digest        │ to internal registry; internal
     status)      │  ≠ pinned digest after copy           │ digest == pinned digest
                  │                                       ▼
                  │                                  Deployable ◀──────────────┐
                  │                                       │                    │
                  │                     ready replicas ≥  │      ready replicas
                  │                     replicas.min      │      < replicas.min
                  │                                       ▼                    │
                  │                                   Deployed ────────────────┘
```

| From | To | Trigger |
|---|---|---|
| Declared | Syncing | `spec.cluster` matches the CR's namespace through the blue/green map (D14) |
| Declared | Rejected | cluster/namespace mismatch |
| Syncing | ConformanceRunning | tag resolved to a digest at the model-center registry; digest written to `spec.modelRef.digest` and `status.pinnedDigest`; image manifest extracted; CR `model`/`version` match the image's `model-manifest.yaml` (D9) |
| Syncing | Rejected | CR `model` or `version` disagrees with the image's own manifest |
| Syncing | Syncing | model-center registry unreachable → requeue with exponential backoff (D6) |
| ConformanceRunning | Deployable | conformance report all-pass **and** the image copied to the internal registry reads back with a digest equal to the pinned one (D8) |
| ConformanceRunning | Rejected | report has failing checks (nonconformance, no retry) — or the internal-registry digest differs from the pinned digest after the copy (loud, explicit reason) |
| ConformanceRunning | ConformanceRunning | `VerifyImage` returned an error, or the internal registry is unreachable → infrastructure failure, requeue with backoff (D6) |
| Deployable | Deployed | the Deployment's ready replicas reach `replicas.min` (D4) |
| Deployed | Deployable | ready replicas fall below `replicas.min` (D4) |
| Rejected | — | terminal (D5) |

**Manifest failures are caught before conformance runs.** Extraction, schema
validation (`manifest.Load`) and the CR cross-check all happen in `Syncing`,
because D13 needs the manifest to build the Deployment and D9 needs it to
validate the CR. So an image with no manifest, or one whose manifest violates
`contract/manifest.schema.json`, is `Rejected` during `Syncing` with the reason
in `status.message` and **`status.conformance.failed` left empty** — it never
reaches `ConformanceRunning`, so no report exists. This is the same verdict
`msp-conform` reaches as C1, by a different route; the C1 check ID appears only
when `msp-conform verify` is run directly. Acceptance item 4 picks its fixture
accordingly.

**D5 — `Rejected` is terminal.** The digest is pinned and immutable, so the
controller never looks at the tag again; re-pushing a "fixed" image to the same
tag changes nothing that the controller can see. Recovery is to delete the CR
and declare a new version — consistent with §5.4's rule that version strings,
including previously-Rejected ones, are never reused. The Rejected object with
its failure report *is* the record. Alternative rejected: letting the user
clear `spec.modelRef.digest` to trigger a retry — that violates "digest, once
written, is immutable", the one invariant everything else here leans on.

**D4 — `Deployed` reflects reality.** Status describes the present, not the
past: if ready replicas fall below `replicas.min`, the object drops back to
`Deployable`. This also makes "pods will not start" visible in plain
`kubectl get modeldeployments` instead of a forever-green `Deployed`.

**D6 — retry only what retrying can fix.** The line is already drawn by the
existing API: `VerifyImage`'s error return means infrastructure failure only; a
nonconformant image is a Report with failing checks, not an error
(`msp/internal/conformance/docker.go`). The controller follows that line
verbatim: infrastructure failures (docker broken, a registry unreachable) stay
in the current phase and requeue with exponential backoff; a failing report is
`Rejected` with no retry, because rerunning the same gate on the same immutable
digest can only produce the same verdict.

## 3. End-to-end flow

From `kubectl apply` to a ready pod, naming who does what:

1. **Operator / acceptance script** — `kubectl apply -f
   deploy/clusters/green/deployments/defect-cls-v1.yaml` (stand-in for ArgoCD
   sync of the same tree).
2. **API server** — admits the CR against the committed, `controller-gen`-generated
   CRD schema.
3. **msp-sync (host process)** — reconcile begins. Validates `spec.cluster`
   against the CR's namespace via the two-entry map (D14); mismatch →
   `Rejected`.
4. **msp-sync + go-containerregistry** — resolves `model:version` at the
   model-center registry (port 5010) to a digest; writes it to
   `spec.modelRef.digest` and `status.pinnedDigest`. From here the tag is dead
   to the platform.
5. **msp-sync + host Docker** — extracts `/opt/msp/model-manifest.yaml` from
   the image (the `docker create` + `docker cp` logic refactored out of
   `VerifyImage`, cached by digest — D13) and cross-checks the CR's
   `model`/`version` against the manifest's `model.name`/`model.version`
   (D9); mismatch → `Rejected`. Phase → `ConformanceRunning`.
6. **msp-sync goroutine + msp/internal/conformance** — `VerifyImage` runs
   against the digest reference in the background (D12); reconcile returns
   immediately. `VerifyImage` passes the reference straight to the `docker`
   CLI, so a `host/repo@sha256:…` reference works unchanged. On completion the
   object is requeued.
7. **msp-sync + go-containerregistry** — on an all-pass report, copies the
   image manifest byte-for-byte from the model-center registry to the internal
   registry (port 5011), reads the internal digest back, and asserts it equals
   the pinned digest (D8). Equal → `Deployable`; different → `Rejected`, loudly.
8. **msp-sync** — builds Deployment, Service and HPA from the cached image
   manifest (resources, port, startup budget) and the CR (`replicas`), with
   `ownerReferences` pointing at the CR (D19), and applies them in the CR's
   namespace. The pod image is the internal-registry digest reference.
9. **kubelet** — pulls from the internal registry, starts the pod. The gRPC
   `startupProbe` polls the SDK's `grpc.health.v1` service (D7/D17), which
   answers not-serving until `load()` returns, then serving.
10. **msp-sync** — sees ready replicas reach `replicas.min` → `Deployed`.

Deletion is the same flow in reverse minus the controller: `kubectl delete
modeldeployment` → Kubernetes garbage-collects the owned Deployment, Service
and HPA (D19). No finalizer. The image stays in the internal registry, per
§5.4's permanent-retention rule.

## 4. The ModelDeployment CRD

Matching spec §5.2, with Phase 1's constraints called out below:

```yaml
apiVersion: msp.platform/v1
kind: ModelDeployment
metadata:
  name: defect-cls-v1
  namespace: msp-green
spec:
  modelRef:
    source: model-center   # maps to a registry address: hardcoded map + flag override
    model: defect-cls      # must equal the image manifest's model.name (D9)
    version: v1            # must equal the image manifest's model.version (D9)
    digest: ""             # written once by the controller after resolution; immutable after
  cluster: green           # must map to the CR's namespace (blue → msp-blue, green → msp-green)
  replicas: {min: 2, max: 8}
status:
  phase: ""                # Syncing | ConformanceRunning | Deployable | Deployed | Rejected
  pinnedDigest: ""         # sha256:… — same value as spec.modelRef.digest
  conformance:
    passed: []             # e.g. [C1, C2, C3, C4, C5, C6, C7]
    failed: []             # stable check IDs; what acceptance item 4 asserts on
  message: ""              # human-readable reason, populated on Rejected
```

Where Phase 1 constrains or leaves out what §5.2 sketches:

- **Resource override (SPEC-GAP).** §5.2 carries the comment "resources come
  from model-manifest; only overriding the ceiling is allowed here" — but
  defines no field for it. Per spec §11 general requirement 4 ("don't
  implement what the spec doesn't define"), Phase 1 defines no such field:
  resources come from the image manifest, unmodified. Flagged as SPEC-GAP;
  closing it means the spec defining the field first.
- **`status.message`** is the one status field beyond §5.2's sketch. It exists
  because D8 demands a "loud, explicit reason" on a digest mismatch, D5 makes
  the Rejected object the record, and acceptance item 4 requires the failing
  check to be named. It is a plain string, matching the flat style of §5.2's
  status sketch; Kubernetes `conditions` would be a larger surface than any
  Phase 1 consumer reads, and moving to them later is additive.
- **`spec.cluster`** is a logical target validated against the namespace, never
  a write target of its own — see D14 below.
- **HPA metrics**: only `msp_inference_inflight` is emitted (D18). §5.2's
  auxiliary DCGM GPU-utilization metric is not emitted: it needs GPUs and a
  DCGM exporter, neither of which exists locally. Deferred with the rest of the
  metrics stack — see Stand-ins.

## 5. Contract and identity

### D7 — readiness signalling (SPEC-GAP + frozen-interface change)

Kubernetes cannot read the contract's `ModelService.Health`: native gRPC
probes speak only the standard `grpc.health.v1` protocol. Resolution: the SDK
**additively** registers a standard `grpc.health.v1` health service on the same
server, whose serving status mirrors the same `ready` flag `serve()` already
flips (`servicer.ready` in `contract/sdk-python/msp/__init__.py`). Unchanged:
the envelope proto, the `msp.BaseModel` and `msp.serve()` signatures, and the
startup-order contract (gRPC server starts *before* `load()`, so both health
surfaces answer not-ready while loading — the behaviour check C2 depends on).

Changed: `grpcio-health-checking` becomes a dependency of
`contract/sdk-python/pyproject.toml` and therefore of `msp-base` (it is not one
today). This touches CLAUDE.md frozen interface #3 (the scientist SDK surface):
additive, but it **must be flagged in the commit message and gets a decision
ticket on wayfinder map #1** — flagged here so it is opened, not silently
skipped.

Alternatives rejected, and why:

- **TCP probe** — wrong: the port is open before `load()` completes, so
  loading pods would enter the Service and receive traffic they cannot answer.
- **exec probe** — forks a Python interpreter every few seconds, per pod,
  forever.
- **controller polls `Health` itself** — leaves the Service's endpoints
  unguarded (readiness is what removes a pod from endpoints) and breaks
  rolling updates, which key off pod readiness.
- **vendor upstream `health.proto` into `contract/proto/`** — avoids the
  dependency but plants a foreign proto in the directory CLAUDE.md calls "the
  only source of truth for every message". A dependency is honest; a copied
  foreign contract is not.

### D8 — one digest, verified

A Version has exactly one Digest, and CONTEXT.md's invariant — "the verified
one and the deployed one must be the same digest" — is made mechanically true,
not assumed:

1. resolve the source digest from the model-center registry;
2. pin it into `spec.modelRef.digest` and `status.pinnedDigest`;
3. run conformance against that digest reference (`VerifyImage` takes it
   unchanged — it never issues an explicit `docker pull`, relying on
   `docker create`/`docker run` pull-if-missing);
4. copy the image manifest **byte-for-byte** into the platform's internal
   registry;
5. read the internal digest back and **assert it equals the pinned digest**;
   any difference → `Rejected` with a loud, explicit reason.

Implementation: `github.com/google/go-containerregistry` **as a Go library**.
No external CLI — `buildx`, `crane`, `skopeo` and `regctl` are all absent from
the dev machine, and a library call is one fewer thing to install and one fewer
thing to parse. The obvious-looking alternative — `docker pull` + `docker tag`
+ `docker push` — is exactly the path that would *break* the invariant: it
collapses a multi-arch index into a single-platform manifest with a different
digest, silently. The assertion in step 5 exists so that even a future bug in
step 4 fails loudly instead of deploying an unverified identity.

### D9 — the CR is checked against the image

`spec.modelRef.model` and `.version` are cross-checked against the image's
`/opt/msp/model-manifest.yaml` (`model.name`, `model.version`). Either
mismatching → `Rejected`. The manifest inside the image is the model center's
own statement of what the image *is*; disagreement means someone pushed the
wrong image — precisely the class of mistake a conformance gate exists to
catch. Consequence: the acceptance script publishes the example image as
`defect-cls:v1`, matching the version its manifest already declares.

## 6. State, persistence and failure

### D10 — no registry DB in Phase 1 (STAND-IN)

All state lives in the CRD `status`. Accepted consequence: deleting and
redeclaring a ModelDeployment re-runs conformance, so spec §5.4's "conformance
results are reused for redeployment" is **not** honoured yet. Re-running is
idempotent and costs about a minute locally, which is a fair price for shipping
zero database code in a phase that doesn't otherwise need one. Closed when the
registry DB lands in Phase 5.

### D11 — version uniqueness is not enforced here (SPEC-GAP)

Spec §5.4 requires version strings to be unique per model and never reused —
including versions that were Rejected. Enforcing that needs cross-CR,
cross-time state: a deleted CR's history is invisible to both an admission
webhook and a same-namespace scan, so either would be a half-gate that passes
exactly the reuse cases §5.4 most cares about. Per spec §10.1-6, illegal
transitions are rejected by msp-api, which arrives in Phase 5; Phase 1 records
the gap instead of building a gate that cannot see.

### D12 — conformance runs in the background

A conformance run takes about a minute; a reconcile that blocks for a minute
stalls the controller's whole work queue. The controller starts conformance in
a goroutine, returns from reconcile immediately, tracks in-flight runs in a
table keyed by digest — which also yields "at most one run per digest" for
free — and requeues the object on completion. A controller restart loses the
in-flight table; the run simply restarts, which D10 already made idempotent.
Alternative rejected: raising worker concurrency — it only moves the wall, and
it lets concurrent conformance runs contend for the same Docker daemon.

### D13 — the manifest is re-extracted, not stored

At `Deployable`, building the Deployment needs the manifest's resource
requests, port and startup budget — but `conformance.Report` carries only
`{Image, Checks, Pass}`, and there is no database. The extraction logic
already inside `VerifyImage` (`docker create` + `docker cp`) is refactored into
a reusable function, and the controller calls it with an in-memory cache keyed
by digest. Alternative rejected: a `status` field carrying the manifest — that
invents CRD surface the spec does not define, and re-extraction survives a
controller restart with no persistence at all. The image is immutable by
digest, so the extraction is deterministic; a cache is an optimisation, not a
correctness mechanism.

## 7. Reconciliation

### D14 — namespace is the target

Child objects are created in the CR's own namespace. `spec.cluster` is
*validated* against that namespace through a two-entry map — `blue → msp-blue`,
`green → msp-green` — hardcoded in the controller with a flag override; a
mismatch is `Rejected`. No config file: spec §12 Q5's promise that moving to
physically separate clusters only changes the mapping still holds — it just
changes two lines instead of one YAML. Alternative rejected: honouring
`spec.cluster` over the namespace and writing across namespaces — that
requires cross-namespace write permission and decouples the GitOps directory
(`clusters/green/deployments/`) from where things actually land, which is the
one property that makes the tree trustworthy.

`spec.modelRef.source` maps to a registry address the same way: a hardcoded
`model-center → localhost:5010`-style map with a flag override.

### D15 / D16 — what the controller writes, and how often

**D15 — the controller does not fight the HPA.** The Deployment's `replicas`
field is written exactly once, at creation, set to `replicas.min`, and never
touched again. Writing it on every reconcile is the classic controller-versus-
HPA oscillation; omitting it entirely leaves the Deployment at Kubernetes'
default of 1 during the window before the HPA takes effect.

**D16 — every other field is reconciled.** All fields except `replicas` are
driven back to the controller's computed desired state on every reconcile.
This is what a controller is *for*, and it hardens acceptance item 2 beyond
the registry: even a hand-edited image reference on the live Deployment is
pulled back to the pinned internal-registry digest.

### D17 — probes

- **`startupProbe`**: native gRPC probe against `grpc.health.v1`, period 1s,
  `failureThreshold` = the manifest's `startupSeconds` — i.e. exactly the
  budget the contract already declares and conformance check C2 already
  enforces. No second, invented startup budget.
- **`readinessProbe`**: gRPC probe, period 5s, `failureThreshold` 3.
- **No `livenessProbe`.** There is no defensible restart criterion yet, and a
  careless one kills a model that is merely slow — the worst possible failure
  mode for an inference workload.

### D18 — the HPA is generated but inert (STAND-IN)

The HPA is emitted exactly as spec §5.2 requires: the custom metric
`msp_inference_inflight`, never CPU-based. Locally there is no Prometheus
adapter, so it sits at `ScalingActive=False` and never scales. Emitting it
anyway is deliberate: it is what lets the CRD-and-manifest-to-HPA mapping be
tested at all (D21's unit tests assert on the generated object). Alternative
rejected: installing Prometheus locally — that inflates the dev-environment
slice decision D1 deliberately kept small, for a scaler no Phase 1 acceptance
item exercises.

### D19 — deletion is garbage collection

Deployment, Service and HPA carry `ownerReferences` to the ModelDeployment, so
`kubectl delete` lets Kubernetes reclaim them. No finalizer — there is nothing
to clean up that GC does not already cover. The image stays in the internal
registry, per §5.4's permanent-retention rule. This is exactly what acceptance
item 3 asks for, using the platform primitive built for it.

## 8. Build, test, layout

### D20 — one Go module

controller-runtime and its `k8s.io/*` dependencies join the existing `msp/`
module. Go links only what a binary imports, so `msp-conform` does not grow;
only `go.sum` and the first `go mod download` do. Alternative rejected: a
second module — it would force Phase 2's Router, which also watches CRDs, into
the same placement question all over again, and module boundaries are not a
dependency-hygiene tool when one team owns both sides.

### D21 — fake client plus the kind script

Unit tests use controller-runtime's **fake client** for everything that is
pure controller logic: state-machine transitions, digest immutability, the
`spec.cluster`/namespace check, the CR-versus-manifest check (D9), and the
shape of the Deployment/Service/HPA built from a manifest. Real API-server
behaviour — ownerReference garbage collection, pods actually reaching ready —
is covered by the kind acceptance script. Alternative rejected: `envtest` —
the kind script already covers nearly everything it would add, and it costs a
~100MB binary download dependency for the overlap.

### D22 — `make phase1-accept`

`tests/acceptance/phase1_test.sh`, following `phase0_test.sh`'s discipline
exactly: `set -euo pipefail`, a label on every container it starts, `mktemp -d`
scratch, and a `cleanup` trap wired to EXIT plus INT/TERM. One addition to the
pattern: the script detects whether the kind cluster already exists — if it
does, it uses it and leaves it standing; if not, it creates it and tears it
down at the end. Fast on a warm developer loop, still one command from cold.

### Local registries

Two **insecure** local registries, no authentication:

| Registry | Port | Role |
|---|---|---|
| model-center | 5010 | where the model center (the acceptance script) publishes `defect-cls:v1` |
| platform-internal | 5011 | where verified images are copied; what pods pull from |

Both are reachable from kind nodes via containerd configuration.

### Layout

New layout — this **changes `docs/SCAFFOLDING.md`**, which declares its own
changes breaking and requiring a decision ticket on wayfinder map #1. Said
explicitly: **that ticket is to be opened as part of Phase 1, not silently
skipped** (the same ticket flow as D7's SDK-surface change).

```
msp/api/v1/                    ModelDeployment types, controller-gen markers, generated deepcopy
msp/internal/syncctl/          the controller
msp/cmd/msp-sync/              the binary
deploy/                        GitOps tree, shaped by spec §9
  clusters/{blue,green}/deployments/
  routes/                      empty until Phase 2
  platform/crd/                generated CRD YAML, committed
  platform/namespaces.yaml     msp-blue / msp-green, committed, applied by the acceptance script
  policies/
tests/acceptance/phase1_test.sh
```

## 9. Acceptance

The three items from spec §11 Phase 1, plus one added here:

1. Declaring a ModelDeployment drives it automatically to `Deployed` with its
   pod ready.
2. The model center overwriting the same version tag leaves the platform's
   reference untouched — the pinned digest still governs.
3. Deleting the CRD reclaims the associated resources.
4. *(added)* A Phase 0 negative fixture lands in `Rejected` — it does not
   hang. The fixture is `msp-neg-c3-bad-status`, with its failing check named
   in `status.conformance.failed`. It has to be a fixture that reaches
   `ConformanceRunning`: the two C1 fixtures are rejected earlier, in
   `Syncing`, with an empty `conformance.failed` and the reason in
   `status.message` (see §2). Every fixture inherits the example model's
   `model.name`/`model.version`, so D9's cross-check never pre-empts the check
   under test.

what closes it.
